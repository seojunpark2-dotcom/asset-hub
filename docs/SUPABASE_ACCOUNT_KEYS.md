# Supabase에서 계좌 키 받기 · 1.13.0

Supabase Secrets에 보관한 개인 기관 키를 로그인한 소유자의 등록 기기만 받아 Android Keystore로 암호화한다. 키 값은 JS 브리지 응답·화면·로그·저장소·APK에 포함하지 않는다. 기관 잔고 조회는 계속 휴대폰에서 직접 수행한다. Supabase에서 대신 기관에 접속하거나 고정 IP를 제공하는 방식이 아니다.

## 사용자 설정

1. Supabase 대시보드에서 asset-hub → Edge Functions → Secrets → Add secret을 연다. 프로젝트 Publishable key는 수정하지 않는다.
2. 키움 실전 REST 앱키는 `KIWOOM_APP_KEY`, 앱시크릿은 `KIWOOM_APP_SECRET`에 저장한다.
3. 업비트 자산조회 전용 Access Key는 `UPBIT_ACCESS_KEY`, Secret Key는 `UPBIT_SECRET_KEY`에 저장한다. 주문·출금 권한은 부여하지 않는다. 이용하는 기관의 두 항목만 있어도 된다.
4. 앱을 업데이트하고 기존 본인 계정으로 로그인한다. 설정 → 계좌 자동 연동에서 사용할 Wi-Fi를 등록하고 각 공인 IPv4를 기관 허용 IP에도 등록한다.
5. ‘Supabase 키 등록 상태 확인’ → 기관별 ‘Supabase에서 키 가져오기’ → 자산 교체 동의 순서로 진행한다. 기존 수동 입력 키는 그대로 유지되므로 다시 가져오기 전까지 사용할 수 있다.
6. 등록 Wi-Fi에서 정상 잔고를 받으면 앱과 위젯에 반영한다. 기관별·기기별 한국 날짜 하루 한 번 제한은 키를 다시 받아도 초기화하지 않는다.

키를 교체하면 Secrets를 수정한 뒤 ‘Supabase 키 다시 가져오기’를 누른다. 이후 백그라운드 조회는 암호화된 기기 키를 재사용하며 매번 로그인 JWT나 키를 내려받지 않는다. 로그아웃·연결 해제·휴대폰 교체 후에는 다시 가져와야 한다. 연결 해제는 서버 Secrets를 지우지 않는다. 완전 폐기는 기관에서 키를 폐기하고 Secrets도 삭제한다.

## 서버 권한과 검증

- `ACCOUNT_KEY_OWNER_USER_ID`: 키 소유자의 Supabase Auth 사용자 UUID. 기존 사용자 한 명을 확인한 뒤 해당 사용자로 설정했다. 첫 요청 사용자 자동 등록, 이메일 추정, 사용자 수정 가능 metadata를 권한 근거로 사용하지 않는다. 계정 변경 시 운영자가 이 항목을 명시적으로 바꾼다.
- `credential-status`: 서버 `auth.getUser`로 로그인 검증 및 소유자 대조 후 기관별 키 존재 여부만 반환한다.
- `credentials`: 위 검증과 함께 기기 UUID·해시된 64자리 기기 토큰·만료·동일 소유자·직접 조회 scope를 검증한다. 공개 anon JWT나 위젯 토큰만으로는 키를 받을 수 없다. 응답은 `Cache-Control: no-store`이다.
- Android 네이티브 코드가 HTTPS로 키를 직접 받고 즉시 암호화한다. 리다이렉트·HTTP 캐시는 사용하지 않는다. 사용자 JWT는 이 요청에서만 쓰며 계좌 키 보관소에 저장하지 않는다. 저장 직전 로그인 사용자를 다시 확인한다.
- 서비스 역할 키는 Edge Function에만 존재한다. 일반 테이블에 기관 키를 저장하지 않으며 DB 스키마·기존 RLS는 변경하지 않았다. 기존 APK의 로컬 조회·스냅샷 경로를 보존했다.

단위·격리된 서버 검증과 실제 APK 확인은 배포 검증 문서를 따른다. 실제 개인 키를 이용한 잔고 조회·Wi-Fi 및 절전 상태 동작은 휴대폰에서 확인해야 한다.
